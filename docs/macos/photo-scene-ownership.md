## Shared clear boundary

`C_GameApp::OnRender` calls `photoCapture.OnAppRender` before the ordinary `RenderNow` / `BeginRender` scene. `C_PhotoCapture::RenderSingle` calls `RenderStart` before its sample loop. `C_AppPhotoCapture::RenderStart` calls `C_AccumulateStrip::Start`; `Start` calls `ClearTextures`, which binds and clears the three real accumulation render targets. Only the later `RenderAddSample` begins its sample scene. The lower native clear requires an active command stream. This is also why native `OnCreateVolatile` already had a temporary scene around its initial clears.

The normal post-race Lua `SpRaceAwards_TakePhoto` requests `Amax.TakePhoto(1,false,false)` through its original timeline/skip flow. It does not need an operator to force a race result or issue a photo call externally. The captured last232 UI observation was SpFinished, so that observation alone does not establish which subsequent results timeline had begun. MAC237 confirms the shared clear-boundary defect independently without forcing any race completion.

MAC240 moves the existing native owned-scene policy to `ClearTextures`, the boundary shared by volatile creation and capture-start. A caller with an active scene lends it; successful or failed clearing never closes that borrowed scene. Otherwise clearing must successfully begin and retire its own scene, including exception cleanup. Resource rollback remains at `OnCreateVolatile`, where those render textures were acquired. No lower guard, Windows flow, screen-strip copy, source rendering, sample count, photo material or results state is changed.
